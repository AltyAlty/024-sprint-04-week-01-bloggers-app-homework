В созданных NestJS проектах всегда нужно проверять наличие следующих настроек в файле "tsconfig.json" (опция
""strict": true" уже включает в себя эти настройки):
1. Строгая проверка null и undefined: "strictNullChecks": true.
2. Включение удобного импортирования CommonJS-модулей через "import default": "esModuleInterop": true.

Чтобы использовать Nest CLI в приложении для генерации каких-то шаблонных сущностей, команды нужно запускать из папки
приложения с флагом "g". Флаг "--no-spec" будет говорить Nest CLI не создавать файл для тестов.

/*--------------------------------------------------------------------------------------------------------------------*/

NestJS - это высокоуровневая настройка над Express.js, где последний отвечает за низкоуровневые составляющие, например,
принимает HTTP-запросы, работает с сокетами, отправляет ответы клиенту, а NestJS предоставляет архитектуру, то есть
модули, контроллеры, декораторы и DI-контейнер.

Вместо Express.js можно использовать, например, Fastify. Последний работает быстрее и хорошо подходит для
высоконагруженных сервисов, но имеет меньше готовых плагинов и не так широко используется как Express.js.

/*--------------------------------------------------------------------------------------------------------------------*/

В NestJS модули, контроллеры, сервисы, репозитории и так далее создаются в виде классов и помечаются специальными
декораторами, например, "@Module()", "@Controller()" или "@Injectable()", для того чтобы NestJS создавал экземпляры этих
классов.

/*--------------------------------------------------------------------------------------------------------------------*/

В NestJS в качестве точки входа в приложение вместо файла "index.ts" обычно используется файл "main.ts".

/*--------------------------------------------------------------------------------------------------------------------*/

Для установки глобального префикса для всех маршрутов в NestJS, чтобы все маршруты начинались, например, с "/api/",
используется специальный метод, который регистрируется в файле "main.ts": "app.setGlobalPrefix('api')".

/*--------------------------------------------------------------------------------------------------------------------*/

Контроллеры в NestJS отвечают за обработку входящих HTTP-запросов, связывая их с соответствующими методами бизнес-слоя,
которые реализуют бизнес-логику. Контроллеры принимают запросы, делегируют задачи соответствующим сервисам и возвращают
ответы клиенту. Они определяют маршруты и методы, которые могут быть вызваны клиентами, например, через REST API.

Каждый метод контроллера обычно ассоциирован с определенным HTTP-методом (GET, POST, PUT, DELETE и так далее) и
маршрутом, который определяет, как запросы должны быть обработаны.

Основные функции контроллеров:
1. Обработка HTTP-запросов: Контроллеры принимают запросы от клиентов.
2. Маршрутизация: Контроллеры связывают запросы с соответствующими методами, которые должны их обрабатывать.
3. Делегирование бизнес-логики: Контроллеры сами по себе не содержат бизнес-логику, а делегируют ее сервисам.
4. Формирование ответов: Контроллеры возвращают ответы клиентам после обработки запросов.

/*--------------------------------------------------------------------------------------------------------------------*/

Пример простого контроллера в NestJS:

import { Controller, Get } from '@nestjs/common';

@Controller('users')
export class UsersController {
    @Get()
    getAll() {
        return 'This action returns all users';
    }

    @Get('default-category')
    getMyBooks() {
        return 'This action returns users by default category';
    }
}

В этом примере:
1. "@Controller('users')" - это декоратор, который помечает класс как контроллер и определяет базовый маршрут для всех
методов внутри этого контроллера.
2. "@Get()" - это декоратор, который определяет метод как обработчик GET-запросов для маршрута "/users".
3. "@Get('default-category')" - это декоратор, который определяет метод как обработчик GET-запросов для маршрута
"/users/default-category".
4. Значение, которое возвращается из метода контроллера отправляется NestJS в качестве response body (аналог в
Express.js - "res.send()"). Если возвращается объект, то он обычно сериализуется в JSON, а если возвращается строка, то
она отправится как тело ответа. Можно возвращать не только обычные значения, но и, например, "Promise" или "Observable".

Пример дополненного контроллера в NestJS:

import {
  Body,
  Controller,
  Delete,
  Get,
  HttpCode,
  HttpStatus,
  Param,
  Post,
  Query,
} from '@nestjs/common';
import { UsersQueryRepository } from '../infrastructure/users.query-repository';
import { UserViewDto } from './view-dto/users.view-dto';
import { UsersService } from '../application/users.service';
import { CreateUserInputDto } from './input-dto/users.input-dto';

@Controller('users')
export class UsersController {
  constructor(
    private usersQueryRepository: UsersQueryRepository,
    private usersService: UsersService,
  ) {}

  @Get(':id')
  async getById(@Param('id') id: string): Promise<UserViewDto> {
    return this.usersQueryRepository.getByIdOrNotFoundFail(id);
  }

  @Get()
  async getAll(@Query() query: any): Promise<UserViewDto[]> {
    return this.usersQueryRepository.getAll();
  }

  @Post()
  async createUser(@Body() body: CreateUserInputDto): Promise<UserViewDto> {
    const userId = await this.usersService.createUser(body);

    return this.usersQueryRepository.getByIdOrNotFoundFail(userId);
  }

  @Delete(':id')
  @HttpCode(HttpStatus.NO_CONTENT)
  async deleteUser(@Param('id') id: string): Promise<void> {
    return this.usersService.deleteUser(id);
  }
}

В этом примере:
1. Декоратор "@Param()" используется для получения значения ID из URI-параметров.
2. Декоратор "@Query()" используется для получения query-параметров.
3. Декоратор "@Body()" используется для получения данных из тела запроса.
4. Декоратор "@HttpCode()" используется для указания статуса кода успешного ответа клиенту (аналог в Express.js -
"res.status()").
5. Декоратор "@Post()" помечает метод как обработчик Post-запроса.
6. Декоратор "@Delete()" помечает метод как обработчик DELETE-запроса.

/*--------------------------------------------------------------------------------------------------------------------*/

В NestJS слой роутеров обычно не выделяется отдельно, потому что маршруты объявляются прямо в контроллере через
декораторы.

/*--------------------------------------------------------------------------------------------------------------------*/

В NestJS контроллеры живут внутри модулей. Модули являются основными строительными блоками приложений на NestJS. Каждый
модуль инкапсулирует функциональность, объединяя связанные компоненты. Модули помогают организовать код, делая его более
модульным, понятным и легко масштабируемым.

Для чего используются модули:
1. Группировка функциональности: модуль позволяет объединять связанный код в единую структуру. Например, можно иметь
модуль для работы с базой данных, модуль для пользовательского интерфейса и так далее.
2. Изоляция кода: модули позволяют скрыть детали реализации от других частей приложения.
3. Повторное использование: модули позволяют повторно использовать компоненты в разных частях приложения.
4. Зависимости и импорт/экспорт: модули могут иметь зависимости от других модулей и экспортировать свои компоненты для
использования другими модулями.

Модуль в NestJS - это класс, помеченный декоратором "@Module()". Этот декоратор принимает объект конфигурации, который
включает:
1. Массив "imports" - это массив модулей, которые необходимы для работы данного модуля. Текущий модуль будет иметь
доступ к экспортированным провайдерам указанных модулей.
2. Массив "controllers" - это массив контроллеров, которые обрабатывают HTTP-запросы и возвращают ответы клиенту.
3. Массив "providers" - это массив провайдеров, которые предоставляют сервисы и другую функциональность, используемую
внутри модуля. В том числе здесь должны быть указана функциональность, которая будет экспортироваться наружу.
4. Массив "exports" - это массив провайдеров, которые должны быть доступны за пределами модуля, чтобы другие модули
могли их использовать.

/*--------------------------------------------------------------------------------------------------------------------*/

Каждое приложение на NestJS состоит как минимум из одного модуля - "AppModule", который является корневым модулем. Все
модули должны быть импортированы в "AppModule" напрямую или по цепочке через другие модули.

Примеры модулей:
1. Можно создать модуль "CoreModule" и сделать его глобальным. Это будет означать, что провайдеры, объявленные в этом
модуле, будут доступны для инжектирования в любые другие модули без необходимости их явного импорта. Модуль "CoreModule"
будет включать в себя сервисы и адаптеры, которые могут понадобиться в любом другом модуле приложения. Глобальным модуль
становится если он помечается декоратором "@Global()".
2. Можно использовать модуль "ConfigModule" из пакета @nestjs/config. Этот модуль будет отвечать за работу с переменными
окружения.
3. Можно использовать модуль "MongooseModule" из пакета @nestjs/mongoose. Этот модуль будет отвечать за работу с БД.
4. Можно создать модуль "NotificationModule" и модуль "MailerModule", отвечающий за nodemailer. Модуль
"NotificationModule" будет регистрировать и настраивать модуль "MailerModule". В дальнейшем функциональность модуля
"NotificationModule" может быть расширена другими модулями, например, модулем "TelegramModule". Модуль
"NotificationModule" может содержать сервисы по отправке писем и сообщений в мессенджеры (eventHandlers).
5. Можно создать модуль "TestingModule", который будет содержать контроллер с маршрутом для очистки БД.

/*--------------------------------------------------------------------------------------------------------------------*/

Модули в NestJS позволяют легче следовать DDD.

Нет единого стандарта по каким правилам формировать модули приложения. Можно следовать принципу Low Coupling High
Cohesion. Low Coupling означает, что модули системы должны иметь как можно меньше зависимостей друг от друга. High
Cohesion означает, что все элементы внутри одного модуля должны быть тесно связаны и работать над решением одной и той
же задачи или группы задач. Например, блоги, посты, комментарии можно выделить в один модуль, так как эти элементы
довольно сильно связаны между собой и разбиение их на отдельные модули может вызывать циклическую зависимость между
ними.

Например, сущности "Auth" и "Users" могут иметь очень много циклических зависимостей и при этом обе сущности работают с
пользователями, поэтому их можно объединить в один модуль, чтобы добиться Low Coupling. Или, например, сущности "Blogs",
"Posts" и "Comments" могут и не иметь циклических зависимостей, но при этом эти сущности очень тесно связаны, так как по
сути в реальном использовании приложения почти никогда не будут существовать в изоляции друг от друга, поэтому их можно
объединить в один модуль, чтобы добиться High Cohesion.

NestJS имеет механизм для разрешения циклической зависимости - "forwardRef", однако, и его использование далеко не
всегда является хорошей практикой, поскольку само наличие циклической зависимость, скорее всего, означает, что
архитектура приложение нуждается в рефакторинге.

/*--------------------------------------------------------------------------------------------------------------------*/

Провайдеры в NestJS - это классы, которые NestJS может инжектировать в другие классы с использованием механизма
DI. Провайдером может быть любой класс (или любое другое значение), помеченный декоратором "@Injectable()". Провайдеры
служат для инкапсуляции бизнес-логики, доступа к данным или предоставления других сервисов, необходимых приложению.

NestJS автоматически создает экземпляры классов, помеченных декоратором "@Injectable()", и внедряет зависимости в
конструктор в нужной последовательности. Нужно только лишь зарегистрировать провайдеры в массиве "providers" модуля.
Этот процесс похож на то, как работают IoC-контейнеры в библиотеках, таких как InversifyJS, которые также используют
reflect-metadata для работы с метаданными.

/*--------------------------------------------------------------------------------------------------------------------*/

Модули в NestJS не могут существовать полностью независимо друг от друга, так как провайдеры одного модуля могут
понадобиться в другом. Например, в модуле "UserAccountsModule" могут находиться "UsersExternalService" или
"UsersExternalRepository" - провайдеры, который содержат методы для работы с пользователями. Эти методы могут
потребоваться в других модулях, таких как "BloggersPlatformModule" для бизнес-логики при работе с блогами. Чтобы такие
провайдеры были доступны в других модулях, их необходимо экспортировать из исходного модуля и импортировать в модули,
где они требуются.

Чтобы использовать провайдер в другом модуле, то сначала нужно экспортировать этот провайдер из его исходного модуля.
Для этого нужно добавить его в массив "exports" в этом модуле. После этого, если мы импортируем исходный модуль в другой
модуль, то все экспортированные провайдеры станут доступными для использования в новом модуле.

Часто, для упрощения, из модуля экспортируется весь сервис или репозиторий, даже если во внешнем коде требуется всего
один или два его метода. В результате за пределами модуля становится доступной вся логика сервиса или репозитория, что
может нарушить инкапсуляцию. Чтобы избежать этого нужно использовать специальные урезанные версии сервисов и
репозиториев (ExternalServices и ExternalRepositories) для предоставления только необходимых методов.

Примеры модулей:

Файл "app.module.ts":

@Module({
  imports: [
    MongooseModule.forRoot('mongodb://localhost/nest-bloggers-platform'),
    UserAccountsModule,
    TestingModule,
    BloggersPlatformModule,
    CoreModule,
  ],
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}

Файл "user-accounts.module.ts":
@Module({
  imports: [
    MongooseModule.forFeature([{ name: User.name, schema: UserSchema }]),
  ],
  controllers: [UsersController, AuthController, SecurityDevicesController],
  providers: [
    UsersService,
    UsersRepository,
    UsersQueryRepository,
    SecurityDevicesQueryRepository,
    AuthQueryRepository,
    UsersExternalQueryRepository,
    UsersExternalService,
  ],
  exports: [UsersExternalQueryRepository, UsersExternalService],
})
export class UserAccountsModule {}

Файл "bloggers-platform.module.ts":
@Module({
  imports: [UserAccountsModule],
  providers: [BlogsService],
})
export class BloggersPlatformModule {}

В этом примере:
1. В модуле "AppModule":
1.1 В массиве "imports" указано, что внутри модуля будет использоваться функционал, указанный в массивах "exports"
других модулей, а конкретно модулей "UserAccountsModule", "TestingModule", "BloggersPlatformModule" и "CoreModule".
Модуль "MongooseModule" является динамическим, то есть его нужно настраивать при импорте, поэтому вызывается метод
"forRoot()" для подключения к БД. Метод "forRoot()" может принимать объект с опциями вторым параметром.
1.2 В массиве "controllers" указано, что внутри модуля будет использоваться контроллер "AppController".
1.3 В массиве "providers" указано, что внутри модуля будет использоваться функционал, имеющий отношение к сущности, с
которой работает модуль, а конкретно сервис "AppService".
2. В модуле "UserAccountsModule":
2.1 В массиве "imports" указано, что внутри модуля функционал динамического модуля "MongooseModule", а конкретно
вызывается функция "forFeature()" для регистрации конкретной модели.
2.2 В массиве "controllers" указано, что внутри модуля будут использоваться контроллеры "UsersController",
"AuthController" и "SecurityDevicesController".
2.3 В массиве "providers" указано, что внутри модуля будет использоваться функционал, имеющий отношение к сущности, с
которой работает модуль, а конкретно сервисы и репозитории "UsersService", "UsersRepository", "UsersQueryRepository",
"SecurityDevicesQueryRepository", "AuthQueryRepository", "UsersExternalQueryRepository" и "UsersExternalService". Сервис
"UsersExternalService" и репозиторий "UsersExternalQueryRepository" по факту могут не использоваться внутри модуля, но
указаны здесь, чтобы их можно было указать в массиве "exports".
2.4 В массиве "exports" указано, что извне в других модулях может переиспользоваться внутренний функционал текущего
модуля, а конкретно сервис "UsersExternalService" и репозиторий "UsersExternalQueryRepository".
3. В модуле "BloggersPlatformModule":
3.1 В массиве "imports" указано, что внутри модуля будет использоваться функционал, указанный в массивах "exports"
других модулей, а конкретно модуля "UserAccountsModule".
3.2 В массиве "providers" указано, что внутри модуля будет использоваться функционал, имеющий отношение к сущности, с
которой работает модуль, а конкретно сервис "BlogsService".
4. В каждом файле экспортируется пустой класс, но декоратор "@Module()" вешает на каждый модуль мета-данные. В nestJS
задача классов модулей не хранить логику, а быть носителем метаданных модуля.

Модули обычно работают с сущностями. Пример сущности:

/**
 * User Entity Schema
 * This class represents the schema and behavior of a User entity
 */
@Schema({ timestamps: true })
export class User {
  /**
   * User login (must be unique)
   * @type {string}
   * @required
   */
  @Prop({ type: String, required: true, unique: true })
  login: string;

  /**
   * User password hash for authentication
   * @type {string}
   * @required
   */
  @Prop({ type: String, required: true })
  passwordHash: string;

  /**
   * User email
   * @type {string}
   * @required
   */
  @Prop({ type: String, required: true })
  email: string;

  /**
   * User email confirmation status (account will be deleted, if not confirmed after 2 days)
   * @type {boolean}
   * @default false
   */
  @Prop({ type: Boolean, required: true, default: false })
  isEmailConfirmed: boolean;

  /**
   * "@Prop(NameSchema)" does not validate object
   */
  @Prop({ type: NameSchema })
  name: Name;

  /**
   * Timestamps creation
   * @type {Date}
   */
  createdAt: Date;
  updatedAt: Date;

  /**
   * Deletion timestamp (null if not deleted)
   * @type {Date | null}
   */
  @Prop({ type: Date, nullable: true })
  deletedAt: Date | null;

  /**
   * Factory method to create User instances
   * @param {CreateUserDomainDto} dto - The DTO for user creation
   * @returns {UserDocument} - The created user document
   */
  static createInstance(dto: CreateUserDomainDto): UserDocument {
    const user = new this();
    user.email = dto.email;
    user.passwordHash = dto.passwordHash;
    user.login = dto.login;
    user.isEmailConfirmed = false;

    user.name = {
      firstName: 'firstName xxx',
      lastName: 'lastName yyy',
    };

    return user as UserDocument;
  }

  /**
   * Marks the user as deleted
   * @throws {Error} If the entity is already deleted
   */
  makeDeleted() {
    if (this.deletedAt !== null) throw new Error('Entity already deleted');
    this.deletedAt = new Date();
  }

  /**
   * Updates a user instance with new data
   * Resets email confirmation if email is updated
   * @param {UpdateUserDto} dto - DTO for user updating
   */
  update(dto: UpdateUserDto) {
    if (dto.email !== this.email) {
      this.isEmailConfirmed = false;
      this.email = dto.email;
    }
  }
}

export const UserSchema = SchemaFactory.createForClass(User);
UserSchema.loadClass(User);
export type UserDocument = HydratedDocument<User>;
export type UserModelType = Model<UserDocument> & typeof User;

В этом примере:
1. Декоратор "@Schema()" помечает класс как Mongoose-схему.
2. Флаг "timestamps" автоматически добавляет поля "updatedAt" и "createdAt" в схеме.
3. Декоратор "@Prop()" определяет поле схемы с настройками. В этом декораторе можно делать глубокую валидацию как схемах
Mongoose, но также стоит делать дополнительную валидацию в Input DTO при помощи декораторов из пакета class-validator.
4. Комментарии в данном примере не влияют на код, они написаны в формате JSDoc для документирования и подсказок в IDE.
5. Явно создаются поля "createdAt" и "updatedAt" без декоратора "@Prop()" в классе, так как флаг "timestamps" создает
эти поля только в схеме и документах и TypeScript о них не знает.
6. Метод "SchemaFactory.createForClass()" создает схему на основе класса.
7. Код "UserSchema.loadClass(User)" регистрирует методы класса "User" в схеме, чтобы они были доступны на документах.
8. Тип "UserDocument" используется для типизации документов.
9. Тип "UserModelType" используется для типизации модели со статическими методами класса "User".
10. Как работает код "const user = new this()" в статическом методе "createInstance()": в рамках статического метода
this обычно указывает на сам класс "User". Но в момент регистрации модели, Mongoose по сути сделает следующее:
"const UserModel = mongoose.model('User', UserSchema)", где "UserModel" будет конструктором, который наследуется от
класса "User". В итоге вместо "User.createInstance(dto)" будет вызываться "UserModel.createInstance(dto)". TypeScript
будет считать, что this это класс "User", поэтому приходится приводить тип через оператор as -
"return user as UserDocument".
11. В методе "makeDeleted" происходит soft delete - документ не удаляется из БД, а помечается как удаленный.
12. Эта сущность следует элементам DDD:
12.1 Сущность создается через статический метод.
12.2 Изменение сущности происходит инкапсулировано, то есть вызываются методы сущности для изменения состояния сущности
по правилам этой сущности.

/*--------------------------------------------------------------------------------------------------------------------*/

Мапперы можно реализовывать как статический метод-утилита, что упрощает его повторное использование в разных частях
приложения. Альтернативным подходом является использование конструктора для выполнения этой задачи.

/*--------------------------------------------------------------------------------------------------------------------*/

В NestJS удобно описывать Input DTO в виде классов. Это связано с тем, что во время выполнения NestJS автоматически
создает экземпляры этих классов. Это упрощает валидацию и трансформацию данных, например, санитизацию, с помощью
специальных декораторов. Output DTO тоже иногда делают в виде классов для единообразия.

/*--------------------------------------------------------------------------------------------------------------------*/

В контексте NestJS, pipe - это обработчик входных данных до вызова метода контроллера. Pipes похожи на middlewares, но
pipes не срабатывают на весь запрос, а конкретно на аргументы метода контроллера (body, query или params) прямо перед
тем, как они попадут в метод. Также pipes знают, какой метод контроллера будет вызван, когда middlewares не могут этого
знать. Главная цель pipes - валидация и трансформация.

/*--------------------------------------------------------------------------------------------------------------------*/

Декоратор "@InjectModel()" - это декоратор из @nestjs/mongoose, который работает через DI-контейнер NestJS. В этом
декораторе надо указывать имя класса и это удобно делать через свойство "name" классов, которое содержит имя классов в
виде строки. Декоратор "@InjectModel()" просит NestJS найти и внедрить зарегистрированную через метод
"MongooseModule.forFeature()" в модуле готовую модель Mongoose.

/*--------------------------------------------------------------------------------------------------------------------*/

Декоратор "@ApiParam()" - это декоратор из @nestjs/swagger, который используется для генерации документации API. Этим
декоратором помечается метод контроллера и в нем указывается параметр, для которого должна быть сгенерирована
документация.

/*--------------------------------------------------------------------------------------------------------------------*/

Чтобы в NestJS выбрасывать разные коды статусов ответа клиента, нужно просто выбрасывать соответствующие ошибки - NestJS
автоматически перехватит ошибку и сформирует соответствующий код статуса ответа клиенту.

/*--------------------------------------------------------------------------------------------------------------------*/

В NestJS по умолчанию синглтонами являются:
1. Модули.
2. Контроллеры.
3. То, что указано в массиве "imports".
4. То, что указано в массиве "controllers".
5. То, что указано в массиве "providers".
6. То, что указано в массиве "exports".

Это поведение можно изменить через свойство "scope" в декораторах "@Injectable()" и "@Controller()".

/*--------------------------------------------------------------------------------------------------------------------*/

В методах контроллера можно возвращать промисы. NestJS под капотом сам делает await (или оборачивает результат в
"Promise.resolve()") на то, что возвращает метод. NestJS дожидается момента выполнения промиса и автоматически
отправляет полученные данные клиенту.

/*--------------------------------------------------------------------------------------------------------------------*/

При создании схемы, используя декоратор "@Schema()", можно использовать флаг "{ _id: false }", который будет говорить
Mongoose не создавать автоматически поле "_id" для этой схемы.

/*--------------------------------------------------------------------------------------------------------------------*/

В NestJS все типы можно переводить на классы, так как после компиляции в JS-код типы исчезают, а классы остаются на
месте, что позволяет NestJS читать метаданные, создаваемые декораторами.

Когда не стоит переводить тип на класс в NestJS:
1. В случае простых псевдонимов: "export type SortDirection = 'asc' | 'desc';".
2. В случае внутренней типизации функций.
3. В случае типизации документов БД.
4. В случае сложных комбинаций типов.
5. В случае типизации Output DTO, когда не используется автоматическая документация Swagger.
