Не стоит экспортировать что-либо из файлов, которые являются точками входа в приложение во избежание повторного запуска
приложения. Например, NestJS имитирует запуск приложения в e2e-тестах и выполнение функции "bootstrap()" создаст
серьезные проблемы при тестировании.

/*--------------------------------------------------------------------------------------------------------------------*/

Data Transfer Object (DTO) - это объект для передачи данных между слоями, у которого есть только поля, методы доступа к
ним и вспомогательные методы, но нет собственных методов для бизнес-логики.

Anemic Model - это объект или класс для представления бизнес-сущности внутри приложения, у которого есть идентичность
(ID), состояние (поля) и методы доступа к нему, но нет собственных методов для бизнес-логики.

Plain Old Java/JavaScript Object (POJO) - это обычный объект или класс, не привязанный к фреймворку, не требующий
наследовать чужой класс и реализовать обязательный интерфейс.

/*--------------------------------------------------------------------------------------------------------------------*/

Презентационный слой также называют контроллером.

/*--------------------------------------------------------------------------------------------------------------------*/

Слой Repository - это один из паттернов проектирования, позволяющий разделить логику взаимодействия с БД от
бизнес-логики, что дает следующие преимущества:
1. Чистота и структура кода: роутеры избавляются от логики работы с БД.
2. Легкость тестирования: репозиторий можно тестировать независимо от остальных частей приложения.
3. Гибкость: если структура или тип БД изменятся, то все изменения нужно будет сделать только в репозитории, не
затрагивая другие части приложения.

/*--------------------------------------------------------------------------------------------------------------------*/

В приложение может добавляться слой адаптеров. Адаптеры нужны, чтобы адаптировать какой-то сторонний функционал для
приложения.

/*--------------------------------------------------------------------------------------------------------------------*/

Basic authorization - это способ аутентификации в веб-приложениях, при котором клиент передает серверу логин и пароль в
виде строки, закодированной в формате base64. Этот метод не является безопасным, если не используется с протоколом
HTTPS. Порядок работы этого способа условно такой:
1. Клиент при отправке запроса должен указать в заголовке HTTP следующее:
Authorization: Basic <base64-encoded-credentials>
2. Чтобы получить строку для Basic авторизации, нужно соединить логин и пароль через двоеточие, а затем закодировать
результат в формат Base64.
3. Сервер извлекает данные, декодирует их и проверяет логин с паролем. Если они верны, то сервер разрешает доступ.

/*--------------------------------------------------------------------------------------------------------------------*/

OpenAPI 3.0 - это спецификация для описания RESTful API в формате JSON или YAML.

При CQRS сервисы не должны возвращать данные, завязанные на view моделях или Output DTO. При CQRS, query-репозитории
имеют свои методы для операций чтения. Разделение репозиториев нужно, чтобы сервисы читали данные при помощи методов
только из обычных репозиториев, а UI - при помощи методов только из query-репозиториев.

Для query-репозиториев могут создаваться query-сервисы (query-handlers), где часто происходит маппинг данных. Без
query-сервисов маппинг данных, скорее всего, стоит делать в query-репозиториях.

Методы для чтения в обычном репозитории и в query-репозитории могут отличаться тем, что в репозитории не делается
маппинг данных. Так делается, поскольку подразумевается, что данные полученные из обычного репозитории при чтении не
будут отправляться в UI.

При CQRS также могут разделяться БД. Плюсы такого подхода:
1. Дублирование данных в таком случае повышает отказоустойчивость и доступность.
2. Распределение нагрузки из-за распределения операций.
3. Упрощает распределение ролей касательно доступов к БД.

/*--------------------------------------------------------------------------------------------------------------------*/

ResultObject - паттерн в бэкенд-разработке, используемый для унификации ответов API, обработки ошибок и передачи
дополнительных метаданных. Примерно может выглядеть так:

{
  "success": true,
  "data": { /* полезная нагрузка */ },
  "error": null,
  "message": "Операция выполнена успешно",
  "statusCode": 200,
  "meta": {
    "page": 1,
    "total": 100
  }
}

или

{
  status: ResultStatuses.NotFound,
  data: null,
  errorMessage: 'Not Found',
  extensions: [{ field: 'userId', message: 'Not Found' }], /* массив дополнительных данных об ошибках */
}

При использовании паттерна ResultObject обычно не выбрасываются ошибки, а формируются соответствующие ResultObjects в
BLL.

Для систем логирования часто используется стек ELK:
1. E - Elasticsearch (поисковая система и хранилище).
2. L - Logstash (обработчик и конвейер логов).
3. K - Kibana (интерфейс для дашбордов и графиков).

ELK собирает все логи в одном месте, индексирует их и позволяет строить графики и оповещения:
1. Logstash забирает логи отовсюду (с файлов, по сети, из очередей), парсит, фильтрует, добавляет дополнительную
информацию и пересылает дальше.
2. Elasticsearch хранит логи в виде JSON-документов и позволяет быстро осуществлять поиск по ним, используя разные
критерии и фильтры.
3. Kibana представляет собой веб-интерфейс, где можно писать запросы к Elasticsearch и визуализировать полученные данные
в виде графиков, дашбордов, карт и таблиц с логами.

ELK может быть расширен до Elastic Stack, где вместо или в дополнение к Logstash используется Beats - легковесные
сборщики логов прямо на серверах:
1. Filebeat: читает файлы логов, отправляет в Logstash или сразу в Elasticsearch.
2. Metricbeat: собирает метрики CPU, память и так далее.
3. APM: отслеживает производительность приложений.

Заголовок "origin" в запросах позволяет определить протокол, домен и порт клиента, например, "https://example.com:1234"
или "http://localhost:3000". Но нужно всегда помнить, что порт опускается, если он стандартный - 80 для HTTP и 443 для
HTTPS.

Заголовок "referer" в запросах позволяет определить полный URL, включая путь и параметры (без фрагментов после "#"),
адреса страницы, с которой клиент перешел на текущий URL, например, "https://example.com/products?category=books&page=2"
или "http://localhost:3000/search?q=express".

Не всегда есть возможность использовать cookies на клиенте. В таких случаях для хранения секретных данных, например,
пары AT/RT, может быть использовано следующее:
1. Мобильные приложения используют защищенные на уровне операционной системы и устройства хранилища, например, Keychain
(iOS), EncryptedSharedPreferences (Android) или KeyStore (Android).
2. Десктопны приложения используют системные менеджеры учетных данных, например, macOS Keychain, Windows Credential
Manager или Linux Secret Service.
3. Server-to-Server приложения используют переменные окружения и системные хранилища секретов, например, HashiCorp
Vault или AWS Secrets Manager.
4. CLI используют локальные файлы с ограниченными правами доступа и системные службы управления секретами в ОС
(Keyring), например, Keychain Access (macOS), GNOME Keyring (Linux), KWallet (Linux) или Credential Manager (Windows).
5. Браузерные расширения используют специальные API, доступные только внутри браузерных расширений, например,
browser.storage.local или chrome.storage.sync.

Чтобы получать максимальное представление о пользователе нужно собирать следующие категории данных:
1. Данные об устройстве и приложении, используемые пользователем.
2. IP-адрес пользователя.
3. Геолокация пользователя.
4. Данные о поведении пользователя в браузере.

Чтобы собирать максимум из перечисленных данных, необходимо использовать помимо бэкенда, еще и фронтенд:
1. Во фронтендах используется Fingerprinting библиотеки - специальные библиотек для сбора данных о пользователе со
стороны фронтенда с целью формирования уникального портрета пользователя. Такие библиотеки позволяют собирать, например:
- Разрешение экрана и глубину цвета.
- Список установленных шрифтов.
- Параметры видеокарты.
- Аудио-контекст (разные звуковые карты дают разный шум).
2. В бэкендах используются:
- Библиотеки для парсинга заголовков запросов клиентов.
- Библиотеки для получения реального IP-адреса пользователя.
- Библиотеки для получения геолокации пользователя.
Библиотеки для парсинга заголовков запросов клиентов позволяют собирать, например:
- Марку и модель устройства пользователя.
- Тип устройства пользователя.
- Версию ОС, которую использует пользователь.
- Данные о браузере пользователя и его движке.
- Архитектуру процессора (через заголовки Client Hints "Sec-Ch-Ua").
- Модель устройства (более точно, чем через User-Agent, через заголовки Client Hints "Sec-Ch-Ua").
Библиотеки для получения геолокации позволяют собирать, например:
- Страну, город и координаты пользователя.
- Название провайдера пользователя.
- Тип соединения пользователя.

Классификация бекендов по архитектурному стилю:

1. Монолит - это одно большое приложение. Подходят для небольших или средних приложений с маленькими командами
разработки или если нужно быстро сделать продукт.
Признаки:
- Имеют один кодовый проект.
- Развертывание через один деплой.
- Часто используют всего одну БД.
- Все модули приложения живут внутри одного процесса.
Плюсы:
- Проще проектировать начало приложения.
- Проще отлаживать.
- Проще осуществлять локальны запуск.
Минусы:
- Со временем сильно разрастаются.
- Сложнее масштабировать по частям.
- Не всегда легко вносить изменения, так как они могут задеть другие части приложения.

2. Микросервис - это приложение, которое разбивается на много маленьких независимых сервисов. Подходят для больших
приложений, требующих масштабируемости, с большими или несколькими командами разработки.
Признаки:
- Каждый сервис имеет отдельный запуск и деплой.
- У каждого сервиса может быть своя БД.
- Сервисы общаются по HTTP, gRPC, брокеру сообщений и так далее.
Плюсы:
- Приложение можно масштабировать по отдельным сервисам.
- Разработчики разных сервисов могут работать независимо.
- Удобнее для очень больших систем.
Минусы:
- Имеют более сложную инфраструктуру.
- Сложнее отлаживать.
- Часто имеют проблемы с сетевым взаимодействием, консистентностью или мониторингом.

3. Макросервисы - это приложение, которое разбивается на несколько больших сервисов. Является средним между монолитами и
микросервисами. Подходят для монолитов, требующих разбиения на части, или когда приложение еще недостаточно большое для
разбиения на микросервисы.
